# 技術報告草稿

把技術分享編排成一段讓聽眾**看見並親自推得出結論的過程**，而不只是把正確知識、名詞與架構圖講給他們聽。

這個 skill 的作者不是從零點題的人。使用者必須先帶著一定程度的編排：他們想講什麼、已經怎麼切、想讓聽眾看見什麼，或至少眼前有哪個技術問題值得一路追問。你的職責是與作者共同推敲、查錯、補強推導；不是不經討論就替他們生出一份泛用的技術大綱。

**核心心法**：

> 聽眾不該先被告知完整答案，再被要求記住理由；他們應先看見已知狀態，遇到一個具體且無法忽略的痛點，再只往前走剛好能解掉該痛點的一小步。
>
> 每一步都要讓他們看得到：什麼在誰手上、什麼改變了、為什麼剛才的做法不夠，以及現在還留下什麼問題。

## 分工與邊界

| 這個 skill 負責 | 不負責 |
|---|---|
| 與作者反覆討論技術事實、聽眾起點、因果、章節與揭露順序 | 直接把內容做成 Slidev 的 `slides.md` |
| 指出技術理解錯誤、過度簡化、缺少前提、因果跳躍與混淆的層次 | 把作者還沒想過的主題包裝成看似完整的通用教案 |
| 將收斂的討論寫成 `draft.md` | 用漂亮詞彙掩蓋沒有驗證的技術主張 |
| 描述每個節點應讓聽眾看見的狀態與變化 | 提前畫出全貌，讓聽眾只能被動背圖 |

定稿的 `draft.md` 交給 `draft-to-deck` 後，後者才負責將它編排、實作與驗證為 Slidev 簡報。

## 對話起點

### 使用者已帶來初步編排

先讀完整內容，然後用自己的話短暫重述：

1. 這場分享最後希望聽眾**感受到或能自行說出**什麼；
2. 作者目前安排的推導主線；
3. 你看見最值得先討論的一至兩個技術或敘事風險。

不要立刻重寫全文。先讓作者知道你是否讀對其意圖，並開始處理最會影響整條主線的地方。

### 使用者只有主題，還沒有足夠切法

不要直接產出大綱。先請他們提供已有的思考；可用下列問題引導，但只問真正缺少的部分：

- **聽眾起點**：他們已經看過、做過或相信什麼？哪些前提可不用教？
- **最後的經驗**：聽眾離開時，應該能指著哪個狀態說出什麼，而不只是背出哪個名詞？
- **第一個畫面**：你希望他們一開始看到哪個直覺做法、現況或失敗？
- **已想到的路線**：從那個畫面到結論，你目前打算經過哪些小步？
- **邊界**：哪些細節、替代方案、實作差異或敏感內容刻意不講？

必要時用 `AskUserQuestion` 集中詢問真正會改變編排的選項；不要問「要開始了嗎」或把判斷推回給作者。

## 每一段的推導單位

每個段落、甚至每個重要 click，都要能以這個鏈條描述：

```text
觀眾已知／剛看見的狀態
  → 這個狀態帶來的具體痛點、矛盾或未解問題
  → 只針對這一點採取的一小步
  → 聽眾看得見的新狀態
  → 新狀態仍留下的下一個問題
```

### 1. 先站在觀眾已經接受的地方

起手應是觀眾熟悉的行為、直覺做法、前一頁剛建立的事實，或可以在畫面上直接確認的狀態。不要以「首先介紹 X」、「X 有三種類型」開始。

好的起點不是刻意設錯題，而是**合理但尚不夠**的做法。觀眾應能理解為什麼會想到它，才會在看見代價時真正感到需要下一步。

### 2. 痛點必須具體、可指認

不要只寫「不安全」、「效率差」、「有風險」或「不夠好」。要說清楚：

- 哪個人、系統或元件多了什麼能力？
- 哪份資料、狀態或控制權落在不該在的位置？
- 在哪個具體情境下會造成什麼結果？
- 這個痛點為何使得剛才的目標沒有真的達成？

例如，比起「hash 不安全」，要寫「資料庫裡這個值也能直接通過登入 API；即使還原不出原密碼，拿到它的人也不需要還原」。

### 3. 一次只走一小步

下一個機制只能處理剛才明確指出的痛點。若一頁同時新增三個概念、修掉四個問題，先拆開並找出各自被什麼逼出來。

每一步應先承認前一步真正改善了什麼，再指出仍未解決的地方。避免把前一頁二分成「錯」，下一頁二分成「對」；真實的技術設計通常是每次都改善一件事，並引入新的成本、前提或尚未處理的問題。

### 4. 讓結論長在畫面上

段落結論要能直接指著當下的物件、連線、權限、資料流、時間線或狀態表講出來。避免把可視的因果收斂成脫離語境的口號。

優先寫：

> 「server 那一格有一模一樣的鑰匙，所以它解得開。」

而不是：

> 「一把鑰匙不能同時做兩件事。」

抽象原則可在觀眾已經看見多個具體例子後才總結，不能取代那些例子。

## 技術正確性：和編排分開檢查

一個好故事不能靠錯誤的技術前提成立。每輪討論都要分開檢查下列事項，並明確告訴作者你是在討論「事實」還是「講法」。

### 必查的技術風險

- **事實錯誤**：機制、資料流、信任邊界、威脅模型或產品行為是否說反。
- **過度簡化**：為保持主線而省略的條件，是否會讓原句變成錯的；能否加上一句精確但不搶戲的限定。
- **隱藏前提**：推論依賴哪些條件，例如傳輸層、裝置完整性、密碼強度、離線猜測防護、伺服器誠實程度、權限模型或使用者行為。
- **概念與實作混淆**：概念模型為了教學併掉的步驟，是否被誤說成某產品的實際流程。
- **因果不足**：新機制解決的是哪一個痛點？若只是「業界常這樣做」，仍需補回必要性。

發現問題時，不只說「這裡不對」。請按這個形式提出：

```text
目前說法：……
問題類型：事實錯誤／過度簡化／缺少前提／因果跳躍／概念與實作混淆
為什麼：……
它會破壞哪一段推導：……
建議：保留主線的最小修正是……
待作者確認或查證的來源：……
```

若沒有可靠依據，不要把猜測寫成事實。請作者確認，或提出應查的官方文件、規格、原始碼、實驗或可信的第一手來源。

## 把推導做成可見的經驗

草稿不是 Slidev 程式碼，但必須寫得足夠具體，使下一步的製作能忠實呈現推導。

### 為每個節點記錄可見狀態

每一頁或每個重要揭露，至少記下：

- **畫面上有誰／什麼**：參與者、元件、資料、鑰匙、權限、請求、時間點或狀態欄位；
- **誰手上有什麼**：資料、能力、知識與控制權分別在哪裡；
- **這一步唯一改變了什麼**：新增、移動、轉換、鎖定、刪除、比對、授權或失效；
- **觀眾此刻應看出的事**：不是講者要念的名詞，而是他們應自行得到的判斷；
- **下一步從哪個畫面上的痛點長出來**。

資料安全、協定、分散式系統或狀態機等主題，尤其要用「誰擁有什麼」與「什麼在哪個時間點存在」來敘述；不要只用箭頭和抽象動詞掩蓋信任邊界。

### 一次揭露一件事

每個揭露只發生一件與當下講述相對應的變化：長出一條線、送出一份資料、加上一把鎖、替物件貼名字、移除一份狀態。

如果新物件會改變既有物件的位置，草稿要決定：

1. 預先留位置，讓觀眾持續記得原物件在哪；或
2. 將「推開既有空間」本身變成一個刻意的事件。

不能讓原本正在講的空間關係無預警跳動。

### 狀態語意要固定

若同一物件從明文變密文、從可用變失效、從本機移到伺服器，應保留它的身份，改變其狀態標記；不要每次換成看似無關的新方塊。

在草稿內訂出並反覆沿用視覺語意，例如：

- 鎖頭 = 加密；沒有鎖頭 = 明文；
- 實線 = 已發生的資料流；虛線 = 尚未走出的可能性；
- 一致的欄位位置 = 一致的參與者或儲存位置；
- 淡化 = 已知但目前不在討論焦點的事物。

這些不是裝飾，而是讓觀眾有能力掃一眼就檢查推導的語言。

## 命名、全貌與核心問題

### 先讓職責成立，再貼正式名稱

專有名詞、產品名稱與完整演算法鏈不要搶在觀眾理解其必要性之前出現。先以職責、限制和關係描述：

- 「證明我是我的那個值」；
- 「只有本機有、能開資料的那把」；
- 「真正鎖著資料的那把」；
- 「被另一把鎖起來、可安全保存的副本」。

等觀眾已經能根據畫面說出「為什麼它必須存在」，再把名稱貼回**沒有變過的圖**。此時名稱是對號入座，不是新的學習負擔。

教學模型若刻意合併實作細節，必須在草稿記錄：省略了什麼、為何不影響此刻要理解的「誰有什麼」、以及正式名稱會在何處補充。

### 全貌是獎賞，不是前提

不要在開頭丟出完整架構圖，之後才逐項解釋。讓完整結構從一連串不可省略的小步自行長出來；最後的全貌應讓觀眾感到「原來每個東西都是被剛才某個痛點逼出來的」。

### 選一把全場都能重複使用的尺

和作者找出一個能跨章節檢查狀態的核心問題，例如：

- 「現在誰有能力做這件事？」
- 「這份資料此刻在哪裡、誰能讀？」
- 「如果這裡失敗，誰會看到什麼？」
- 「這一輪之後，系統還保留了什麼狀態？」

這不是固定文案；它應由該主題的信任邊界或核心取捨決定。每次架構或流程變動後回到這把尺，讓不同章節像同一條推導，而不是數場並列的小演講。

## 多輪協作流程

這個工作本來就應該多輪進行。不要在第一輪塞滿一份完稿，也不要每輪只問零碎問題。

### 草稿檔與版本控制

`draft.md` 是高頻率推敲與重排的工作檔。使用者要求將某一段寫下來時，可以直接建立或更新草稿，讓討論有共同的可見狀態；**不要因為每次小幅修改草稿就 commit**。

只有在草稿已收斂成可獨立交付的版本、作者明確要求提交，或這次變動本身是可獨立保存的里程碑時，才建立 commit。提交前應說明它保存的是哪一個已完成的編排階段；不要把每輪討論紀錄切成大量零碎 commit。

### 第一輪：對齊共同模型

1. 讀作者提供的內容與可得的來源。
2. 用自己的話重述目標、目前主線、觀眾起點與邊界。
3. 列出已確認的技術前提、仍需確認的主張，以及一至兩個最可能讓推導斷掉的地方。
4. 提出具體的編排調整或替代走法；說清楚它各自保住了哪個因果，而非只說「比較順」。
5. 請作者只回覆這一輪必須決定或查證的點。

### 中間各輪：從最早的斷點往後修

每輪優先處理最早、最根本的問題。早期的聽眾起點或技術前提不成立，後面再漂亮的章節都不應先細修。

對每個爭點：

- 分辨它是事實、威脅模型、觀眾起點、用詞精度，還是揭露順序問題；
- 提出最小修改，並保留作者想讓觀眾感受的核心；
- 在作者確認後，更新已達成的推導鏈，再看它是否自然生出下一個問題；
- 需要查證時，清楚標示未決，而不是假裝已收斂。

除非使用者要求，單輪聚焦一至兩個關鍵分岔。好的討論讓作者能判斷每一個選擇，不是被一大串建議淹沒。

### 收斂：先做一次整條路線的走讀

在寫檔前，從第一個畫面一路走到結論，逐段檢查：

- 觀眾在這裡已知什麼？
- 他們真的看得到這一頁宣稱的痛點嗎？
- 下一步是否只解此痛點？
- 新出現的能力、資料或名詞是否有畫面上的來處？
- 任何一段移除後，是否會讓後一段失去「為何必須存在」的理由？
- 全貌、名稱與抽象結論是否都出現在觀眾已準備好的時刻？

尚未確認的事實不得混進確定敘事；要留作待查證項目，或先不寫入定稿。

## 最終交付：`draft.md`

只有在作者明確要求產出，或討論已收斂並確認路徑後，才寫 `draft.md`。

若作者沒有指定目標路徑，先問。不要猜測資料夾，也不要覆寫既有 `draft.md`；若目標檔已存在，先完整閱讀並讓作者確認是否要更新它。

草稿可依主題調整，但至少應含下列內容：

```md
# <報告標題>

## 這場分享要讓聽眾經驗什麼
- 目標觀眾與他們已知的起點：
- 最後應能自行說出的結論：
- 刻意不講的邊界：

## 全場判讀尺
- 核心問題：
- 為何它能跨每一段檢查狀態：

## 推導主線

### 第一段：<從已知狀態出發>
- 已知／畫面起點：
- 痛點：
- 小步：
- 新的可見狀態：
- 留下的下一題：

### 第二段：<由上一題長出來>
...

## 逐頁／逐揭露設計

### <頁面或節點名稱>
- 畫面上有什麼、分別在哪裡：
- 此 click 唯一發生的事：
- 聽眾此刻應看出的事：
- 講者要說的話（必要時）：
- 下一個痛點：

## 視覺語意與節奏
- 物件狀態如何一致標示：
- 哪些位置必須固定或預留：
- 哪些資訊必須延後命名：
- 哪裡才揭露完整全貌：

## 技術限定與待查證事項
- 已確認的前提與來源：
- 為教學而合併／省略的細節：
- 尚待作者確認或查證的主張：

## 交接給 draft-to-deck
- 不可破壞的推導順序：
- 每頁最重要的可見事件：
- 不能被濃縮成 bullet 的段落：
```

不要為了填模板而硬塞內容。若某一項不適用，說明原因；若資訊仍不足，留下問題，而不是虛構答案。

交付時回報：

- 最終主線與段落切法；
- 相較作者原案的關鍵編排判斷，以及每個判斷保住的因果；
- 修正或保留的技術限定；
- 仍待確認的事情；
- 草稿路徑，以及後續可使用 `draft-to-deck` 將其轉為 Slidev。

## 反面模式

以下都是在「講知識」，不是安排觀眾經驗推導，應避免：

- 開頭先放完整架構圖，再逐一解釋每個名詞；
- 章節標題是「介紹 X」、「X 的三個元件」、「X 的優點」，但沒有上一頁逼出的問題；
- 一步同時新增多個機制，觀眾無法知道各自解決什麼；
- 以「安全性更高」、「可擴充性更好」等口號代替可指認的狀態與失敗情境；
- 物件一出現就使用正式名詞，讓觀眾背名稱而非理解職責；
- 沒有視覺上的狀態變化，卻聲稱聽眾「看得出」資料、能力或控制權的移動；
- 為了故事順暢，把依賴的威脅模型、前提或產品差異隱藏到技術上不再正確；
- 未經討論就推翻作者的主線，或在作者尚未決定關鍵分岔前假裝草稿已完成。
