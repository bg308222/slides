# 月報草稿

把使用者丟來的多個工作項目，整理成一份**主管與同事看得懂「這個月做了什麼、做到哪、為什麼這樣做」**的 `draft.md`。

參考範例：`slides/innovue/*99-monthly-report/`（`user-draft.md` 是使用者原始輸入，`draft.md` 是整理後的成品）。動手前先讀最近一份的這兩個檔，對齊語氣與粒度。

## 月報和技術分享的差別

| | 月報 | 技術分享（technical-report-draft） |
|---|---|---|
| 主角 | 本月處理的**事件與工作項目** | 一個技術概念 |
| 結構 | 多個並列項目，彼此無關 | 單一推導主線 |
| 每項要回答 | 為什麼要做 → 怎麼做／為什麼這樣選 → 遇到什麼 → **現在狀態** | 聽眾如何一步步自己推出結論 |
| 技術細節 | 只講到足以支撐「決策」與「卡點」的程度 | 是內容本身 |
| 未完成 | 照實寫，並說明卡在誰、等什麼 | 不適用 |

因此不要把月報項目改寫成教學推導，也不要為了「有料」加入使用者沒做的背景知識。
例外：某個點正是本月決策的關鍵（例如攻擊怎麼發生，才知道 workaround 為什麼有效），可以保留簡短說明，但定位仍是「支撐這次的處理」。

## 月報的特性（從過往月報歸納）

1. **狀態是第一等資訊**。每個項目都要有明確狀態：已交付／已完成／已修正／已復原／部分完成／進行中／驗收中／待客戶端驗證……。部分完成要拆到子項各自的狀態。
2. **歸屬寫成「客戶 — 系統: 項目」**。例：`STD — EPSCore: 簽核 error 問題處理`、`慧榮 — EPSNet: 滲透測試缺失修補`。不是客戶專案的內部工作（如工具、plugin）就直接寫名稱。
3. **講決策與取捨，而不是只列做了什麼**。
   - 原本的需求或問題是什麼
   - 直覺做法／過去做法為什麼不採用（成本、風險、時間、框架限制）
   - 實際採用的策略與理由
   這是月報最有價值的部分，使用者常把它壓成一句，要拆出來。
4. **卡點與過程照實呈現**。驗收被 rollback 幾輪、各輪原因；重現不出來；原因不明——都直接寫，不要美化成「順利完成」，也不要替使用者猜原因。
5. **區分「誰的問題」與「等誰」**。來源資料問題、客戶端環境、等待對方確認，要寫清楚，這直接影響狀態判讀。
6. **一句「可以帶到的一點」**。若項目有值得留下的觀察（例如「第一部分只處理被掃出來，第二部分才是真的處理風險」、「備份是唯一保險」），獨立成一行標出來；沒有就不要硬湊。
7. **開頭本月概覽 + 一句主軸，結尾每項一行總結**。主軸是對整個月的觀察（例：「本月主軸偏向既有系統的體質與資安，而非新功能開發」），要從項目本身歸納，不是口號。
8. **保留參考連結**。使用者給的文件、規格、原始碼連結原樣留下，之後放進簡報的參考資料頁。

## 流程

### 1. 決定位置

月報資料夾為 `slides/innovue/YYYYMM99-monthly-report/`，日期末兩碼固定為 `99`。

- 月份以使用者指定為準；沒說時，依今天日期推測（月初多半是寫上個月），並在第一次回覆中明講用哪個月，讓使用者可以更正。
- 若資料夾內已有 `draft.md`，先完整讀過，問使用者要更新還是覆寫。

### 2. 保存原始輸入

把使用者提供的項目內容**原封不動**存成同資料夾的 `user-draft.md`（已存在則先確認）。這是事後比對「整理時有沒有改掉原意」的依據。

### 3. 讀懂並短暫重述

每個項目用一兩句話重述：在處理什麼、目前狀態。同時列出缺的資訊。最常缺的是：

- **狀態**：只描述做了什麼，沒說完成沒
- **為什麼這樣做**：只寫結論，沒寫為什麼不用直覺做法
- **縮寫與內部代號**：無法從上下文判斷的
- **未完成項目的下一步**：等誰、等什麼

用 `AskUserQuestion` 一次問完會改變草稿內容的問題（例如用 multiSelect 勾選已完成的項目）。能從內容判斷的不要問；不要問「可以開始了嗎」。

### 4. 整理

- 用使用者的事實與措辭，補結構、補因果，不補事實。不確定的地方寫成待確認，不要猜。
- 技術說法有明顯錯誤或前後矛盾時，指出來讓使用者確認，不要自行改寫成另一個說法。
- 同一項目內若有多個獨立子項（如滲透測試的三項缺失），編號為 `2-1`、`2-2`…，每個子項各自有狀態。
- 項目順序：沿用使用者給的順序，除非使用者另有指示。

### 5. 寫出 `draft.md`

格式沿用過往月報：**純文字縮排（4 空格），不用 Markdown 標題**。這是給人讀、給 draft-to-deck 拆頁用的條列草稿。骨架：

```text
YYYY 年 M 月月報 — <作者>

本月概覽
    <客戶 — 系統>: <項目> — <狀態>（<一句說明>）
    ...
    <一句本月主軸>

一、<客戶 — 系統>: <項目>

    背景／原始需求／問題本身
        ...

    過去的處理方式／評估        ← 有「為什麼不用直覺做法」時才寫
        ...

    這次的決定／採取策略
        ...
        理由：...

    交付內容／處理過程
        ...

    過程中的觀察／遇到的問題    ← 有才寫
        ...

    結果／目前處置
        ...

    狀態：<狀態>

    可以帶到的一點              ← 有才寫
        ...

二、...

總結
    <客戶 系統> — <一行：做了什麼 + 狀態>
    ...

參考資料                        ← 有連結才寫
    <標題>: <URL>
```

小節名稱依項目性質調整（事件應變類可用「事件發現／處置」，需求開發類可用「原始需求／交付內容」），不要為了填骨架硬塞空小節。作者名沒給時，用 git user 名稱。

### 6. 回報

- 草稿路徑
- 每個項目的狀態一覽
- 整理時補上的因果、拆出的子項，以及仍待使用者確認的地方
- 下一步：確認草稿後可用 `draft-to-deck` 做成 `slides.md`

不要在草稿階段 commit，除非使用者要求。

## 反面模式

- 把項目寫成技術教學：先講三段原理，最後才一句「本月已修正」
- 只列交付物，沒有「為什麼這樣做」
- 未完成項目寫得像已完成，或沒寫卡在哪
- 替使用者推測原因不明的問題、補上沒做過的工作或下月計畫
- 主軸寫成空泛口號（「持續精進、穩定交付」）
- 改掉使用者的專有名詞或客戶名稱寫法
