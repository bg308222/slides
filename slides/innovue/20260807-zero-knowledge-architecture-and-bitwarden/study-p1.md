# Part 1 — 登入方式的漸進式進化

從「直接把密碼存起來」到「兩邊都做一次處理」

先不談任何架構名詞，只看一件事：
**使用者的密碼，在這趟旅程中經過了誰的手？**

## 1. 直接存密碼

註冊：client 把帳號密碼交給 server，server 原封不動存進資料庫
登入：client 再送一次帳號密碼，server 拿出來比對，一樣就放行

資料庫裡長這樣：

| 帳號 | 密碼 |
|---|---|
| andy | hunter2 |

=> 資料庫被偷走，所有人的密碼直接攤在攻擊者眼前，完全沒有緩衝

## 2. 存 hash 過的密碼

改成不存密碼本身，而是存 hash 後的結果，並且每人配一組不同的 salt。

註冊：client 送帳號密碼，server 算完 hash 存起來
登入：client 送帳號密碼，server 用同樣的 salt 重算一次，比對 hash

| 帳號 | salt | hash |
|---|---|---|
| andy | x7Kq… | 9f2a…（反推不回 hunter2） |

=> 資料庫被偷走，攻擊者拿到的是一堆反推不回去的 hash，這關擋住了

**但問題只是換了位置**：使用者打的密碼，還是原封不動送到 server 上，
server 在收到的那一瞬間，看得到 `hunter2` 本人。

於是所有風險都跑到「收到的那一刻」：

- server 被入侵 → 攻擊者在收信的那段程式加一行紀錄，就能坐著收割所有人的密碼
- 開發者為了除錯，不小心把整包請求內容印進 log
- 錯誤追蹤系統、監控工具自動幫你把請求內容存下來
- 公司內部有權限的人（工程師、DBA）看得到
- 最痛的一點：**大家會重複使用密碼。**
  這站的 `hunter2` 外洩，等於他的 Gmail、銀行也一起完蛋

=> 注意這裡的重點**不是「網路傳輸不安全」** —— https 已經把線路保護好了。
   真正的問題是：**密碼有沒有必要讓 server 看到？**

## 3. 讓 server 從頭到尾看不到密碼

既然 server 只是要「比對」，它其實不需要知道密碼本身。

那就讓 **client 先 hash**：

註冊：client 自己把 `hunter2` hash 成 `9f2a…`，只把 `9f2a…` 送出去
登入：client 一樣 hash 成 `9f2a…` 送出去比對

=> 使用者真正的密碼從此不離開自己的裝置，server 從頭到尾沒看過 `hunter2`

**但這樣還不夠。**

因為 server 存的是 `9f2a…`、client 送去比對的也是 `9f2a…` ——
這代表 **`9f2a…` 本身就變成了新的密碼**。

資料庫再被偷一次，攻擊者拿著 `9f2a…` 直接送去登入 API 就進去了。
他確實還原不出 `hunter2`，但他**根本不需要**還原，因為登入只看 `9f2a…`。

等於我們只是把密碼從 `hunter2` 改名叫 `9f2a…`，帳號的安全性一點都沒變。

=> 但這一步仍然有價值，只是價值不在原本以為的地方：
   它保護的是「**這個人**」—— 真正的密碼沒外流，不會波及他其他站的帳號
   它保護不了「**這個帳號**」—— 這站還是照樣被登入

## 4. 兩邊各做一次

第 2 步和第 3 步防的其實是不同的洞，那就**兩個都做**：

```
client 端：hunter2 ──hash──► 9f2a…  ──送出──┐
                                            │
server 端：              9f2a… ──加 salt 再 hash──► c41d… ──存起來
```

- **client hash 的那一層**，讓真正的密碼不離開使用者的裝置 →「保護這個人」
- **server hash 的那一層**，讓資料庫外洩也拿不到能直接登入的東西 →「保護這個帳號」

登入時，client 送 `9f2a…`，server 重算成 `c41d…` 跟資料庫比對。
攻擊者就算偷走整個資料庫，拿到的 `c41d…` 既算不回 `9f2a…`、也算不回 `hunter2`，
送去登入 API 也不會過。

=> 走到這裡，server 從頭到尾沒有在任何時刻、以任何形式持有過使用者的密碼，
   而它仍然能正確地驗證「你是你」。

## 小結

四步走完，我們解決的是「**登入**」這件事。

但如果 server 上還存著使用者的**資料**呢？
密碼藏好了，不代表資料也藏好了 —— 那是完全不同的一道題。

=> p2 繼續
